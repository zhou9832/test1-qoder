## 盈亏平衡估算

### 假设条件

```
人力成本 RPL = 人均每分钟修正行数 = 2 行/min（经验值）
人力成本 rate = $______/hour（请代入你的实际值，以下使用 $50/hour 示例）
```

### C 比 A 每次任务多花的成本

```
C 每次额外 Credits 开销 = C_Credits - A_Credits = 5800 - 2500 = 3300 credits ≈ $3.30 USD

每次节省人工工时 = (A_人工改行 - C_人工改行) / RPL
                 = (280 - 45) / 2
                 = 117.5 min ≈ 2 hours

每次节省人工成本 = 2 hours × $50/hour = $100

净效益 = 节省的人工成本 - 额外的 Credits 开销
       = $100 - $3.30
       = $96.70/task（正效益，C 组划算）
```

### B 比 A 每次任务多花的成本

```
B 每次额外 Credits 开销 = B_Credits - A_Credits = 3500 - 2500 = 1000 credits ≈ $1.00 USD

每次节省人工工时 = (A_人工改行 - B_人工改行) / RPL
                 = (280 - 150) / 2
                 = 130 / 2
                 = 65 min ≈ 1.1 hours

每次节省人工成本 = 1.1 hours × $50/hour = $55

净效益 = $55 - $1.00 = $54/task（正效益，B 组也划算但不如 C）
```

### 盈亏平衡点比较

#### A → B 的盈亏平衡（增加 B 组的投入是否值得？）

```
B vs A 增量投资 = B 前期投入 - A 前期投入 = 0 - 0 = $0（rules 已在第 12 章建成，属沉没成本）

但如果不建 rules（纯 A 组场景），需先投入 S_rules = 3 hours × $50 = $150

每 task 净节省 = $54（来自上节）
盈亏平衡任务数 n_AB = $150 / $54 ≈ 2.8 → **约 3 个任务**

结论: 如果预期同类需求 ≥ 3 次 → 配 rules 划算；否则用裸对话即可。
```

#### B → C 的盈亏平衡（从"只规则"升级到"全套"是否值得？）

```
C vs B 增量投资 = C 全部资产 - B only rules = 12h - 3h = 9 hours × $50 = $450

每 task 净节省 = C_net_benefit - B_net_benefit = $96.70 - $54 = $42.70/task

盈亏平衡任务数 n_BC = $450 / $42.70 ≈ 10.5 → **约 11 个任务**

结论: 如果已有 rules（B 组配置），再花 9 小时升级全套（C 组）的前提是预期同类需求 ≥ 11 次。
```

### 总体盈亏平衡（A vs C 直接比较）

```
前期总投入 S_A-C = C 全部资产 = 12 hours × $50 = $600

每次任务净节省 = C_net_per_task - A_net_per_task
                = ($100 - $3.30) - ($0)  （A 组无额外 Credits 但人工成本高）
                = $96.70/task

盈亏平衡任务数 n_AC = $600 / $96.70 ≈ 6.2 → **约 7 个任务**
```

### 综合决策矩阵

| 预期任务数 | 最优方案 | 累计成本（USD） |
|-----------|---------|---------------|
| ≤ 2 次 | □ A 裸对话 | A = 0×2 + 2×$116.7 = $233<br>B = $150 + 2×$54 = $258<br>C = $600 + 2×$96.7 = $793 |
| 3-6 次 | ☑ B 只规则 | A = N×$116.7<br>**B = $150 + N×$54**（最低）<br>C = $600 + N×$96.7 |
| ≥ 7 次 | ☑ C 全套 | A = N×$116.7<br>B = $150 + N×$54<br>**C = $600 + N×$96.7**（最低） |

**解释**:
- N = 2 时: A=$233, B=$258, C=$793 → **A 最便宜**（适合一次性/探索原型）
- N = 5 时: A=$583, B=$420, C=$1083 → **B 最便宜**（中期项目）
- N = 10 时: A=$1167, B=$690, C=$1567 → 此时 B 仍最低，但如果考虑质量差异（缺陷少、维护成本低）→ **C 开始有竞争力**

> **注意**: 上述计算仅考虑"一次性交付成本"，未计入"质量溢价"（一次通过率高导致的客户满意度、返工机会成本等）。加入质量因素后，C 组的盈亏平衡点会提前。

## C 组扩展机制的成本拆解（诚实呈现代价）

### 三个必须承认的事实（第 13.5 章）验证

1. ✅ **C 组前期投入最大**: S = 12 小时 / $600
   - 如果你的项目只做一两个任务就结束 → C 组是亏的
   - 如果你的项目要做 10+ 次同类任务 → C 组早赚

2. ✅ **C 组首次执行的 Credits 消耗显著高于 A 组**: 
   - C = 5800 vs A = 2500
   - 倍数关系: 5800 / 2500 = **2.32x**（低于预期的 3-5 倍，因 subagent 并行调用而非串行）

3. ✅ **收益随复用次数增长，前期是负的**: 
   - 盈亏平衡点: 
     - A→B: **3 次**（规则的投资回收期短）
     - B→C: **11 次**（全套投资的回收期长）
     - A→C 直接跳: **7 次**（忽略中间步骤）

> "配置越多越省"是错的；配置越多，单次越贵，但返工越少。

## 推广决策树（完整版，基于 A/B/C 三组数据）

```
开始
│
├─ Q1: 本项目预期同类需求会重复多少？
│  ├─ ≤ 2 次 → ➡️ 别重配（采用 A 组轻量方案）
│  │    理由：规则投资还没摊平（n_AB = 3 次才回本）
│  │
│  ├─ 3-6 次 → ➡️ B 组（只规则 v1.1）
│  │    理由：ROI 最佳（$54/task 净节省，3 次回本）
│  │    最小起步集 = charter + 10-java-backend + 20-react-frontend
│  │    （预计前期投入 3 小时，可拦截 ~25% 架构走偏类缺陷）
│  │
│  └─ ≥ 7 次 → ➡️ 继续看 Q2
│
├─ Q2: 是否需要 Hooks 物理拦截（防测试越权）？
│  ├─ 是（多人协作） → ✅ C 全套（必配 Hooks）
│  └─ 否（单人开发） → 继续看 Q3
│
├─ Q3: 是否需要子智能体独立审计（CodeReview + test-engineer）？
│  ├─ 是（高标准质量要求） → ✅ C 全套
│  └─ 否 → B 组（只规则）+ 手动 CodeReview
│
└─ 最终决策:
   □ A 轻量模式（一次性/探索期）
   □ B 标准配置（中期项目，3-6 次复用）
   □ C 全套（长期产品，≥ 7 次复用 + 多人协作 + 高质量标准）
```
