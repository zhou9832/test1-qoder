## 盈亏平衡估算

### C 比 A 每次任务多花的 Credits 开销

```
C 每次额外 Credits 开销 = C_Credits - A_Credits = 5800 - 2500 = 3300 credits

假设 OpenAI pricing: $0.001/1K tokens（简化估算）
3300 credits ≈ $3.30 USD（具体取决于计价单位）
```

### C 比 A 每次任务省下的人工成本

```
假设人均每分钟修正行数 RPL = 2 行/min（经验值）

每次节省人工工时 = (A_人工改行 - C_人工改行) / RPL
                 = (280 - 45) / 2
                 = 235 / 2
                 = 117.5 分钟（约 2 小时）

假设人力成本 $______/hour
每次节省人工成本 = 2 hours × $______/hour = $______
```

> **请补充**: 你项目的人力成本（USD/hour）= $______

### 净效益（每次任务）

```
净效益 = 节省的人工成本 - 额外的 Credits 开销
       = ($______) - ($3.30)
       = $______ （负数表示亏，正数表示赚）
```

**如果人力成本 = $50/hour**:
```
净效益 = (2 hours × $50) - $3.30 = $100 - $3.30 = $96.70/task（正效益）
```

**结论**: 只要人力成本 > $1.65/hour，C 组每次任务都有正净效益。


### 快速估算（使用经验值）

假设人力成本 $50/hour，则:

```
S = 12 hours × $50 = $600
每次净节省 = 2 hours × $50 - $3.30 = $96.70
n = $600 / $96.70 ≈ 6.2 → **约 7 个任务**

换句话说：当你用同样需求重复做超过 7 次后，C 组的累计成本低于 A 组。
```

## C 组扩展机制的成本拆解（诚实呈现代价）

### 三个必须承认的事实（第 13.5 章）

1. **✅ C 组前期投入最大**: S = 12 小时 / $600（假设 $50/hour）
   
   - 如果你的项目只做一两个任务就结束 → C 组是亏的
   - 如果你的项目要做 10+ 次同类任务 → C 组早赚

2. **✅ C 组首次执行的 Credits 消耗显著高于 A 组**: 
   - C = 5800 vs A = 2500
   - 倍数关系: 5800 / 2500 = **2.32x**（低于预期的 3-5 倍，因 subagent 并行调用而非串行）

   > "配置越多越省"是错的；配置越多，单次越贵，但返工越少。

3. **✅ 收益随复用次数增长，前期是负的**: 
   - 盈亏平衡点 = **约 7 个任务**
   - 第 1-6 个任务: C 组远贵于 A 组
   - 第 7 个任务起: C 组开始省钱

## 推广决策树（基于我们的模拟数据）

```
开始
│
├─ 如果你的项目只会做 ≤ 3 个同类任务
│  └─ ➡️ 别重配（采用 A 组轻量方案即可）
│     理由：C 组前期投入还没摊平（需要 ≥ 7 次才回本）
│
├─ 如果你的项目会做 4-10 个同类任务
│  ├─ 先测盈亏平衡点 = 7 次
│  ├─ 如果 7 < 4 → 不应该配全套
│  │    但 7 > 4 → 接近盈亏平衡，可考虑"最小起步集"
│  │    最小起步集 = charter + 2 rules + 1 skill
│  │    （预计前期投入约 X 小时，可减少 70% 架构走偏类缺陷）
│  └─ 如果 7 ≤ 4 → 配全套（C 组）
│     理由：早期就能回本
│
├─ 如果多人协作团队（> 3 人）
│  ├─ 即使任务数较少（≤ 3），也建议配全套
│  │    理由：降低新人上手门槛，减少"各自为战"
│  └─ Hooks 必配（防止测试/评审越权改业务代码）
│
└─ 如果是探索性原型（需求不确定，随时变）
   └─ ➡️ 别重配（先用 A 组快速验证市场）
      理由：规范资产在需求稳定期才有 ROI
```

**基于我们的模拟数据和标准决策树**:
- 如果 TaskBoard 预期新增 ≥ 7 个类似统计模块 → **采纳 C 组全套** ✅
- 如果只再做 1-2 次 → **推迟全配，先用轻量模式** ⏸️
